# The Sync overwrites stored images when the winner's preview changes

The repo contract is "one stored image = the winner's first preview image". Before automation this contract could quietly rot: once an image was stored nothing ever touched it again, so a changed winner (a newer same-named upload, or the same item getting a new preview image) left the stored image permanently out of date. Now that the Sync writes images itself, it also detects staleness: the winner's current `previewUrl` is compared against the `previewUrl` recorded in `index.json`, and a mismatch triggers a re-download that overwrites the stored file. A URL comparison suffices because Steam UGC hands out a fresh preview URL for every newly uploaded image. Two edges follow: a stored map with no index record cannot be judged stale and is left alone, and a winner that lost its preview entirely never deletes the stored image — the repo stays additive in deletions even though it became mutable in content. Hand uploads are deliberately unprotected: they are a fallback for Steam API outages, and the next Sync normalizes them to the winner's actual preview. Consequence for consumers: image content at a stable URL can now change, so indefinite client-side caching is no longer sound. The alternative — keeping images immutable once stored — was rejected because it makes stale content permanent with nobody left to notice, and the daily Sync is exactly the actor that can notice.
